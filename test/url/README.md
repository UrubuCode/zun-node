# node:url — Node.js compatibility tests

The compatibility bar for `url` is **Node.js 25's own test suite**, not tests we
write. `url` is **not finished** until it passes 100% of Node's `test-url*`
tests.

## The oracle

`NODE_TESTS.txt` is the full inventory of Node 25's `test/parallel/test-url*.js`
files — 17 of them. The prefix `test-url` also selects `test-urlpattern*`, and
that is deliberate: `URLPattern` is a `node:url` export in Node 25, so those
files are part of this module's bar rather than a different one's.

```
test-url-domain-ascii-unicode.js           test-url-parse-invalid-input.js
test-url-fileurltopath.js                  test-url-parse-query.js
test-url-format-invalid-input.js           test-url-pathtofileurl.js
test-url-format-whatwg.js                  test-url-relative.js
test-url-format.js                         test-url-revokeobjecturl.js
test-url-invalid-file-url-path-input.js    test-url-urltooptions.js
test-url-is-url-internal.js                test-urlpattern-invalidthis.js
test-url-parse-format.js                   test-urlpattern-types.js
                                           test-urlpattern.js
```

The `test-whatwg-url*.js` files (27 more) are **not** in this corpus: they
exercise the engine's global `URL`/`URLSearchParams` — the prelude classes in
`crates/zun_prelude/builtin/` — rather than anything `node:url` adds on top, so
they belong to the prelude's own bar.

Each file is fetched verbatim from `nodejs/node` at tag `v25.0.0`; nothing is
vendored here.

## How they run

`url` is **not** a `zun_abi` extension. It is pure computation, so it is written
in Zun TypeScript (`../../src/url/url.ts`) and compiled by the platform's own
compiler — no `--ext` library, no syscalls. It stands on `events` (the `ERR_*`
bases), `path` (`fileURLToPath`/`pathToFileURL`, both platforms), `querystring`
(`parse`'s `parseQueryString`) and `punycode`
(`domainToASCII`/`domainToUnicode`), which is why it is inlined last of the
library modules. See `../../PLAN.md`.

```sh
bash tools/run_node_tests.sh --zun <path-to-zun> --module url
```

`internal/url` is in the bundler's module table alongside `internal/util`, for
the same reason: it is `url`'s own implementation surface, not a separate
module, and that is what lets `test-url-is-url-internal.js` ask for `isURL`
under `--expose-internals`.

The four passing `{ skip: !hasIntl }` files — `test-url-format.js`,

`test-url-urltooptions.js` are real passes.

## Security posture

`url.parse` is the one function in this library with a CVE history, and every
guard Node grew for it is reproduced rather than simplified away:

- **CVE-2018-12123** (hostname spoofing through a mixed-case scheme). The
  protocol is lower-cased *before* any `slashedProtocol` / `hostlessProtocol` /
  `unsafeProtocol` decision, so `HTTP://` and `http://` take the same branch.
  The one place Node asks with the literal (non-lowered) protocol is kept
  asymmetric, because that asymmetry is observable.
- **Forbidden host characters.** After IDNA the hostname is re-checked against
  NUL, tab, newline, carriage return, space and `# % / : < > ? @ [ \ ] ^ |`
  (with `[`, `]` and `:` permitted for an IPv6 literal) and an offender raises
  `ERR_INVALID_URL` instead of being moved into the path. NUL is in that set —
  the `http://[127.0.0.1\x00c8763]:8000/` case, i.e. the CVE-2026-48930 class: a
  NUL in a host must neither be accepted nor truncated away. The check runs
  *after* the IDNA step precisely because that step is what can reintroduce such
  a character.
- **An empty hostname after IDNA** also raises `ERR_INVALID_URL`: it was
  non-empty a moment earlier, so it can only have been emptied by `toASCII`, and
  an empty host is exactly what a spoof needs.
- **Hostnames over 255 characters** are dropped to the empty string first, as in
  Node.
- **No regular expressions.** Node uses eight here (`protocolPattern`,
  `portPattern`, `hostPattern`, `simplePathPattern`, `forbiddenHostChars`,
  `forbiddenHostCharsIpv6`, the `file:` protocol test and the slash replacement
  in `getPathFromURLWin32`); each is a hand-written scan, both because a RegExp
  loses its methods through an `any`
  ([zun#7](https://github.com/UrubuCode/zun/issues/7)) and because a URL parser
  is the last place that should own a backtracking engine.
- **Null-prototype query objects.** `parse(url, true)` routes the query through
  `querystring.parse`, which answers a null-prototype object, and the "no query
  string but `parseQueryString` requested" branch builds one directly.

## Engine gaps, and what the module does about them

- **`URL` and `URLSearchParams` are the engine's prelude classes**, re-exported
  here because that is what `node:url` exports in Node. The prelude's WHATWG
  support is partial by its own documentation: no `base` argument, no setters,
  no `URL.canParse`/`URL.parse`, no IDNA, no dot-segment or percent-encoding
  normalization, no `file:` URL with an empty host, and a `URLSearchParams`
  whose `get` answers the empty string rather than `null` and which has no
  `forEach`/`sort`/`size`/iterator. A second class named `URL` cannot be
  declared either — the compiler rejects it with "duplicate class" — so this
  module does not shadow it.
  What it *can* do, and does, is build **genuine prelude `URL` instances** from
  components: a Zun class has no constructor body, so
  `new URL(href, true, scheme, userinfo, host, port, path, query, fragment, params)`
  fills the fields positionally with `loaded` already `true`, the lazy parser
  short-circuits, and every getter answers what we put there. That is how
  `pathToFileURL` returns a real `URL` for `file:///C:/foo` although the prelude
  could not have parsed it, and how `fileURLToPath` turns a `file:` string into
  one. The result is `instanceof URL`, which is what
  `test-url-invalid-file-url-path-input.js` checks.
- **`isURL` is `value instanceof URL`, not Node's duck-type.** Node tests
  `href && protocol && auth === undefined && path === undefined` because its
  `URL` keeps everything in prototype getters and it wants to accept a
  cross-realm URL. Here the duck-type would give the *wrong* answer: the prelude
  `URL` carries an internal field literally called `path`. Identity against the
  class is both correct and what the duck-type stands in for.
- **`domainToASCII`/`domainToUnicode` are punycode, not full UTS#46 IDNA.** Node
  calls into ICU. `punycode.toASCII`/`toUnicode` agree with it for every ASCII
  label — so for every hostname `url.parse` meets in this corpus — and for a
  label already in `xn--` form, and differ on the mapping and normalization
  steps ICU performs for raw Unicode. Node's own
  `test-url-domain-ascii-unicode.js` is written `{ skip: !hasIntl }`, i.e. it
  does not run on an ICU-less build, which is the honest category this runtime
  is in.
- **`fileURLToPathBuffer` is absent**, because `node:buffer` is not implemented
  yet (its own module in `../../PLAN.md`'s roadmap).
- **`Object.assign(target, source)` copies nothing between two class
  instances** on this engine (verified with a probe), and `resolveObject` is
  built on exactly that operation, so `__urlCopyInto` copies the twelve `Url`
  fields by name.
- **A `typeof`-narrowed variable cannot be reassigned to an object.**
  Narrowing `v` with `typeof v === "string"` and then assigning an object to `v`
  makes every later member read on it compile as a *string* member access, and
  the interpreter aborts with `expected object, found Str(…)`. New bug, reported
  with this work; narrowing a *different* binding is unaffected, so
  `__urlResolveObjectFrom` and `__urlFileURLToPath` test the parameter and
  assign to a second name.
- **`host` cannot be a local variable name**: it resolves to the `zun:core`
  `host` namespace, and the checker reports "namespace `host` has no member
  `slice`". Hence `hostText`/`hostPart`/`hostValue`.
- `__urlUnits()` — `charCodeAt(index)` and `slice(from, to)` are O(n) in the
  string's length ([zun#12](https://github.com/UrubuCode/zun/issues/12)), so
  every scan runs over the code-unit array `split("")` produces. The same issue
  makes `path.posix.resolve` O(n²) — 11 seconds for a 10 000-character path —
  which is why `pathToFileURL` first decides in one linear pass whether
  `resolve` is the identity (an absolute posix path every segment of which is
  non-empty and is neither `.` nor `..` has nothing to normalize and no trailing
  separator to strip) and only otherwise calls into `path`.
- `__urlTruthy()` — `!value` mis-reports an `any`-typed empty string as truthy
  ([zun#13](https://github.com/UrubuCode/zun/issues/13)), and `url.parse` is
  full of `this.hostname || ''`-shaped tests on exactly such values.
- `__urlLen()` — the checker types `.length` as `u64`
  ([zun#3](https://github.com/UrubuCode/zun/issues/3)).
- [#37](https://github.com/UrubuCode/zun/issues/37) is designed out rather than
  worked around: `ERR_INVALID_URL`, `ERR_INVALID_URL_SCHEME`,
  `ERR_INVALID_FILE_URL_HOST` and `ERR_INVALID_FILE_URL_PATH` are real
  `TypeError` subclasses with `code` — and, where Node carries one, `input` — as
  **declared** fields, because `test-url-invalid-file-url-path-input.js` reads
  `err.input.href` on exactly such an error.

Uncaught errors are printed as `Object(Obj(0x…))`
([zun#8](https://github.com/UrubuCode/zun/issues/8)), which is why the "Why"
column in `RESULTS.md` is often opaque.
