# `node:worker_threads` against Node.js 25's own tests

The bar for
[`src/worker_threads/worker_threads.ts`](../../src/worker_threads/worker_threads.ts)
is Node's own `test/parallel/test-worker*.js`, `test-messagechannel*.js`,
`test-messageport*.js` and `test-broadcastchannel*.js` at `v25.0.0` — 141
files. The pass count and the per-test table are regenerated by

```sh
bash tools/run_node_tests.sh --zun <path/to/zun> --ext <lib> --module worker_threads
```

and land in [`RESULTS.md`](RESULTS.md); the current figure is **10 / 141** (7.0%).
`worker_threads` is a `zun-ts+ext` module: nothing in it is a syscall, but
twelve files in the corpus require `fs`, `crypto` or `child_process`, and
without `--ext` those bundles fail to compile rather than failing on their real
blocker.

## What the module actually is

`node:worker_threads` is two things wearing one name, and the split decides
everything about this corpus.

* **The message-port family** — `MessageChannel`, `MessagePort`,
  `MessageEvent`, `BroadcastChannel`, `receiveMessageOnPort`, the transfer and
  structured-clone rules, `markAsUntransferable` / `isMarkedAsUntransferable` /
  `markAsUncloneable`, `environmentData`, `SHARE_ENV`, `threadId`,
  `isMainThread`, `parentPort`, `workerData`, `resourceLimits`,
  `postMessageToThread`. Every one of those is **in-process**: a channel is two
  queues and a dispatch rule, and Node's semantics for them are defined without
  reference to a second thread. This half is implemented and is what the module
  is measured on.
* **`Worker`** — a second JavaScript realm on a second thread. The Zun VM has
  one thread and one realm, so there is nothing here for a worker to run *in*.
  **113 of the 141 files construct one**, which is the ceiling on this bar
  until the design in the next section lands.

The `Worker` constructor is nevertheless the real Node constructor down to the
last validation: `options.execArgv` / `options.argv` must be arrays, a
`data:` URL is the eval form, a `file:` URL becomes a path, a non-string
non-URL is `ERR_INVALID_ARG_TYPE`, a relative path that does not start with
`./` or `../` is `ERR_WORKER_PATH` (with the two hints Node adds when the
string looks like a `file:`/`data:` URL), a non-`file:` `URL` is
`ERR_INVALID_URL_SCHEME`, `options.env` must be an object / nullish /
`SHARE_ENV`, `options.name` must be a string, `resourceLimits` members must be
numbers, every `execArgv` entry and every `NODE_OPTIONS` flag must be a
per-isolate option (`ERR_WORKER_INVALID_EXEC_ARGV`), and `options.workerData`
is structured-cloned — so a `workerData` holding a closure is a
`DataCloneError` at construction time. Three of the ten passing files are
exactly those validation paths. Only after all of it does the constructor
report the one honest failure left: there is no thread.

## The design for a real `Worker`

A `Worker` here cannot be a thread, so it has to be a **child Zun process** —
the same trade `child_process.fork` makes, and it keeps every observable fact a
worker has except the shared heap:

* **the script** is a bundle produced by the same `tools/bundle_node_test.sh`
  machinery the tests go through, so the worker script gets this library
  inlined exactly as the parent did; `eval: true` bundles the string instead of
  a file;
* **the handshake** — `isMainThread === false`, `threadId`, `workerData`,
  `environmentData`, `resourceLimits` — is the first frame the parent writes to
  the child's stdin, read by the child's prologue before the script runs;
* **`parentPort`** is a `MessagePort` whose sibling is the pipe rather than
  another in-process port. That is the one seam the implementation needs, and it
  already has it: a port with `__wtSibling === null` delivers nothing, so a
  pipe-backed port is a subclass that overrides `postMessage` and pushes onto
  `__wtQueue` from the reader;
* **the framing** is a 4-byte length plus a [`src/v8/v8.ts`](../../src/v8/v8.ts)
  `serialize` payload, which is V8's value-serialization format — exactly what
  Node puts on a worker's channel (`advanced` serialization in
  `child_process` terms), so the clone rules are reused rather than re-derived;
* **the events** are `online` on the prologue's acknowledgement, `message` per
  inbound frame, `error` for a frame carrying a serialized exception, `exit`
  with the child's code; `terminate()` kills the child and resolves with `1`;
  `stdout`/`stderr` are the child's pipes wrapped as `Readable`s, which
  `src/stream/stream.ts` already gives.

**What differs, and is documented rather than hidden:** a worker gets its own
heap, so a `SharedArrayBuffer` cannot be shared (the engine has none either);
`process.exit()` in a worker ends only the worker, which a child process gives
for free; and `process.env` can only ever be a copy, so `SHARE_ENV` needs a
shared store rather than a pipe and stays a gap.

**The missing piece is a non-blocking read of the child's stdout.** The parent
has to notice an inbound frame without blocking, which needs a poll-based loop
over the pipe. `src/child_process/*.rs` has `std::process::Command` and a
blocking read; the loop is being built on another branch (`src/io/`, not
merged). This module deliberately does **not** grow a socket loop of its own:
when that lands, `Worker` needs the reader above and nothing else, because
every rule a message obeys on the way in and out is already here.

## How a message is delivered

Each `MessagePort` owns its *incoming* queue. `a.postMessage(v)` clones `v`,
pushes the clone onto `b`'s queue and arms one drain of `b`. A drain takes a
snapshot of the queue, empties it and dispatches the snapshot; a message posted
*during* a drain lands in the queue the next drain takes.

A port is created **stopped** and **unref'd**. The first `'message'` listener —
through `on`, `addEventListener` or an `onmessage` assignment — refs and starts
it; removing the last one stops and unrefs it again. That is
`setupPortReferencing` in `lib/internal/worker/io.js`, and it is what
`hasRef()` reports. `close()` detaches both ends instantly (the rule
`test-worker-message-port-transfer-closed.js` states) but the handle outlives
the call by one turn: the messages already queued are still delivered, and only
then does `'close'` fire and `hasRef()` start answering `false`.

### The two macrotask tiers, and why delivery uses both

The VM's loop has no check phase. `src/timers/timers.ts` arms a `setImmediate`
as an engine timer with a **0 ms** delay and a `setTimeout(fn, 0)` as one with
**1 ms** (Node's own clamp), and the VM's virtual clock does not advance while
0 ms work remains:

```js
// zun:  timeout fired, n = 0        node:  timeout fired, n = 5
let n = 0;
function loop() { n++; if (n < 5) setImmediate(loop); }
setImmediate(loop);
setTimeout(() => console.log('timeout fired, n =', n), 0);
```

A drain that re-armed itself on the immediate tier would therefore starve every
timer in the program — which is exactly what
`test-worker-message-port-infinite-message-loop.js` exists to rule out ("the
event loop should be available and not stall out due to the recursive
`.postMessage()` calls"). So the *first* drain of a batch is armed on the
immediate tier, where Node's poll phase sits relative to `setImmediate`, and a
drain armed from **inside** another drain goes on the timer tier instead, which
is the turn Node's loop gives the timers phase once per iteration.

### The hybrid dispatch

Node's `MessagePort` and `BroadcastChannel` are `NodeEventTarget`s: one listener
list serving two calling conventions. A listener added through
`addEventListener` (or an `onmessage` assignment) is handed the `Event`; one
added through `on`/`once`/`addListener` is handed the raw value. The event is
created lazily, so `port.on('message', …)` never allocates one, and for
`'message'`/`'messageerror'` it is a `MessageEvent` carrying `data` and the
received `ports` while every other type gets a `CustomEvent` with `detail` —
which is what makes

```js
port2.addEventListener('foo', (ev) => ev.detail === 'bar');
port2.on('foo', (v) => v === 'bar');
port2.emit('foo', 'bar');
```

call both listeners with the right argument.

## Deviations from Node, each with its cause

| Deviation | Cause |
|---|---|
| `MessageChannel` is declared as `__zunMessageChannel` and the bundler rewrites the Node spelling | the engine's prelude owns the name and a **prelude class cannot be shadowed** — see the new engine bugs below |
| `util.inspect(port)` prints the generic class body instead of `MessagePort [EventTarget] { active: true, refed: false }`, and `bc[util.inspect.custom]` is absent | a symbol-keyed own property on a **class instance** reads back `undefined` (below), so the custom inspector cannot be installed |
| `port.onmessage = fn` is rewritten by the bundler to the backing slot | a class accessor's **setter** is not invoked through an `any` receiver (below); the accessors read and write the very same slot, so both spellings agree |
| an `onmessage` handler dispatches *after* the registered listeners of the same type, not at the position the first assignment put it | the slot is written straight through, with no setter to hook, so there is nowhere to record the position. Only one Windows-skipped block of `test-worker-broadcastchannel-wpt.js` mixes the two |
| a transferred `ArrayBuffer` is **not detached**: its `byteLength` does not become 0 | [zun#38](https://github.com/UrubuCode/zun/issues/38) — an `ArrayBuffer` has no observable surface at all here; a second transfer of the same buffer *is* caught, through a side table |
| a listener sees no `this`; Node's `EventTarget` calls it with the target as the receiver | [zun#1](https://github.com/UrubuCode/zun/issues/1) |
| `Object.getOwnPropertyNames(MessagePort.prototype)` is `[]` | [zun#51](https://github.com/UrubuCode/zun/issues/51) |
| `MessagePort()` / `MessageChannel()` called without `new` raise `ReferenceError` instead of `ERR_CONSTRUCT_CALL_INVALID` / `ERR_CONSTRUCT_CALL_REQUIRED` | a class is not callable in this engine (`K()` is `ReferenceError: K is not defined`) |
| `moveMessagePortToContext` throws `ERR_METHOD_NOT_IMPLEMENTED` after its real pre-flight check (a closed port is still `ERR_CLOSED_MESSAGE_PORT`) | a second realm is a VM facility, like the `vm` module itself |
| `markAsUncloneable` has no effect on `structuredClone` | the prelude owns `structuredClone`; the mark is honoured on the `postMessage` path, which is this module's own |

## New engine bugs found here

Each was reduced to a standalone file and checked against the open **and**
closed issue list.

**1. A prelude class cannot be shadowed: a top-level class of the same name is
`duplicate class`.** Where `src/timers/timers.ts` shadows the timer
*intrinsics* with top-level functions, a prelude *class* is unshadowable, so a
library cannot replace a prelude class with the Node-shaped one:

```ts
class MessageChannel { port1: any = null; }   // [SEM0001] duplicate class
class Response { a: number = 1; }             // same, for any prelude class
```

This is the class analogue of
[zun#85](https://github.com/UrubuCode/zun/issues/85) (the identifier `console`
cannot be a user binding), and it is why `MessageChannel` is bound to a second
name and rewritten by the bundler.

**2. A symbol-keyed own property written on a class instance reads back
`undefined`; the same write works on a plain object.** `Object.defineProperty`
with a symbol key *is* honoured, which is what separates this from
[zun#91](https://github.com/UrubuCode/zun/issues/91) and from
[zun#32](https://github.com/UrubuCode/zun/issues/32)'s function-valued half:

```ts
const S: any = Symbol("s");
class C { a: number = 1; }
const c: any = new C();
c[S] = 42;
console.log(c[S]);                                      // zun: undefined   node: 42
Object.defineProperty(c, S, { value: 7, configurable: true });
console.log(c[S]);                                      // zun: 7           node: 7
const o: any = {}; o[S] = 42;
console.log(o[S]);                                      // zun: 42          node: 42
```

Code site: the dynamic-object store is reached for a plain object but not for a
class instance's expando path (`crates/zun_interp`'s member-write arm for
`Ty::Instance`).

**3. A `number`-typed field of a class that extends a *prelude* class, given a
top-level `const …: number` as its initializer, aborts the VM.** A literal
initializer is fine, an `any` field is fine, and a *user* base class is fine —
only the prelude base trips it:

```ts
const TEN: number = 10;
class A extends EventTarget { n: number = TEN; }
new A();
// thread '<unnamed>' panicked at crates\zun_interp\src\value.rs:157:22:
// expected float, found Any(Any { tag: Float, payload: 4621819117588971520 })
```

Same panic text as [zun#65](https://github.com/UrubuCode/zun/issues/65) (a call
argument is never unboxed), so it is very likely the same missing unbox on the
field-initializer path when the constructor is the derived one of a prelude
class. Worked around here by declaring the field `any`.

**4. A class accessor's setter is not invoked for an assignment through an
`any` receiver — the *getter* is invoked on a read.** With a *typed* receiver
the setter runs and then aborts on a number
([zun#79](https://github.com/UrubuCode/zun/issues/79)); through an `any`
receiver the assignment is silently lost instead, which is the half #79 does
not describe:

```ts
class A { slot: any = null; get x(): any { return this.slot; } set x(v: any) { console.log("setter ran"); this.slot = v; } }
const a: any = new A();
a.x = 1;              // zun: nothing printed, nothing stored   node: "setter ran"
console.log(a.x);     // zun: null                              node: 1
```

With `const a: A = new A()` the setter *does* run and the interpreter then
panics with `expected object, found Any(Any { tag: Float })` — which is #79
still reproducing. Together with
[zun#78](https://github.com/UrubuCode/zun/issues/78) (a function written into a
declared `any` field of a class instance is discarded) and bug 2 above, there is
**no slot on a class instance that plain JavaScript can write a handler
function into**, which is what forced the bundler rewrite of `onmessage`.

**5. A generator method in an object literal returns nothing when called.**
`{ *[Symbol.iterator]() {} }` is a legitimate empty iterable in JavaScript;
here `for`-of over it throws:

```ts
for (const v of { *[Symbol.iterator]() {} }) {}
// TypeError: [Symbol.iterator]() did not return an object        node: zero iterations
```

This is the sole blocker of `test-messagechannel.js`.

**6. `for (… of <non-object>)` aborts the process uncatchably.** Node throws a
catchable `TypeError`:

```ts
function f(v: any): void {
  try { for (const x of v) {} } catch (e: any) { console.log("caught:", e.name); }
}
f(0);
// zun: runtime error: call did not resolve to a method at f      node: caught: TypeError
```

The abort is outside any `try`, so a library cannot probe an unknown value for
iterability without testing `typeof` first — which is what
`__wtReadIterable` does.

**7. [zun#82](https://github.com/UrubuCode/zun/issues/82)'s symptom has
changed.** A generator object's `[Symbol.iterator]` read as a value no longer
aborts; it answers `undefined`, so the iterator protocol by hand declares a
generator non-iterable while `for`-of over the same object works:

```ts
const g: any = (function* (): any { yield 1; })();
console.log(typeof g[Symbol.iterator]);   // zun: undefined   node: function
```
