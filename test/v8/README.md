# `node:v8` against Node.js 25's own tests

The bar for [`src/v8/v8.ts`](../../src/v8/v8.ts) is Node's own
`test/parallel/test-v8-*.js` at `v25.0.0` — 21 files. The pass count and the
per-test table are regenerated by

```sh
bash tools/run_node_tests.sh --zun <path/to/zun> --module v8
```

and land in [`RESULTS.md`](RESULTS.md); the current figure is **8 / 21**.
`v8` is a `zun-ts` module: it needs no `--ext`, because nothing in it is a
syscall.

## What the module actually is

`node:v8` reads like the most engine-bound module in Node's library and is in
fact two unrelated halves:

* **the wire format**, which is pure arithmetic. V8's `ValueSerializer`
  format (version 15) is a tag alphabet, zigzag varints, IEEE-754 doubles and
  an object-reference numbering — all expressible over the engine's `Buffer`
  and a `DataView`. This half is **byte-identical to Node**: the table below
  was produced by running `v8.serialize(value).toString('hex')` under Node and
  under Zun and comparing, and all 53 rows match.
* **the isolate**, which does not exist here. Heap spaces, a sampling
  profiler, a GC event stream and a heap graph are V8 facilities, and this
  runtime has none of them. Those readings are *shape-true and content-empty*:
  the keys, the types and the file formats are Node's, the numbers are what
  the host surface reports, which is nothing. The full resolution table is in
  the header of [`src/v8/v8.ts`](../../src/v8/v8.ts).

The reverse direction is verified against buffers Node wrote, including the
two in `test-v8-serdes.js` that pin the format: the version-13 payload
`ff0d6f2203666f6f5e007b01` reads back as a self-referential object with
`getWireFormatVersion() === 13`, the version-15 payload
`ff0f6f2203666f6f5e007b01` re-serializes to itself, and the unaligned
`ff0d5c0404addeefbe` reads back as `Uint16Array([0xdead, 0xbeef])`.
`Int16Array`, `Float64Array` and `DataView` payloads written by Node also
deserialize into the right view type here — the *reader* constructs the views
itself, so it has none of the writer's limitation below.

## New engine findings, with repros

One of the three below has an open issue already (zun#38); the other two look
new. Each is worked around at its use site in
[`src/v8/v8.ts`](../../src/v8/v8.ts).

### 1. An `ArrayBufferView` reached through `any` reports no type at all (zun#38)

This is the one gap that costs a test. `serialize(value)` takes an `any`, and
from there a view is almost completely opaque:

```ts
const v: any = new Int16Array([1, 2]);
v.constructor                     // undefined   (Node: [Function: Int16Array])
v.BYTES_PER_ELEMENT               // undefined   (Node: 2)
v.byteLength                      // undefined   (Node: 4)
v.length                          // undefined   (Node: 2)
v[0]                              // undefined   (Node: 1)
Object.getPrototypeOf(v)          // null        (Node: Int16Array.prototype)
v instanceof Int16Array           // false       (Node: true)
Object.prototype.toString.call(v) // "[object Object]"  (Node: "[object Int16Array]")
ArrayBuffer.isView(v)             // true        <- the only signal
Buffer.isBuffer(v)                // false       <- true only for the U8 family
Object.values(v)                  // [1, 2]      <- the elements, but not their width
JSON.stringify(v)                 // {"0":1,"1":2}
```

So the only two observable facts are *that* it is a view and whether it is a
`Uint8Array`/`Buffer`. Re-typing works when the declared type matches —
`function f(v: any): Int16Array { return v; }` then `f(v).length` is `2` — and
is an **uncatchable** runtime error when it does not (`zun: runtime error:
call did not resolve to a method`, which escapes `try`/`catch`), so the kind
cannot be probed either. The consequence is documented at the top of
`src/v8/v8.ts`: a `Buffer`/`Uint8Array` serializes exactly as Node does it,
and any other view raises a data clone error naming this gap. The same
blindness covers `ArrayBuffer`, which through an `any` is indistinguishable
from `{}`.

This is **zun#38**, which already lists `length`, the index read,
`byteLength`, `byteOffset`, `buffer`, `constructor` and the class tag. Two
refinements measured here, against that issue's text: `Object.keys(v)` is no
longer empty (it answers `["0", "1"]` for a two-element view, so the element
*count* is recoverable), and `Object.values(v)` / `Array.from(v)` /
`JSON.stringify(v)` now read the real element **values**. What is still
missing is the element *width*, which is exactly what the wire format needs,
so the gap costs `test-v8-deserialize-buffer.js` either way.

### 2. A function assigned onto a class instance is lost (looks new)

```ts
class A { n: number; constructor() { this.n = 1; } }
const a: any = new A();
a.yyy = function (v: any): string { return "Y" + String(v); };
typeof a.yyy        // "undefined"   (Node: "function")
a.yyy(3)            // TypeError: yyy is not a function

const o: any = {};
o.yyy = function (v: any): string { return "O" + String(v); };
typeof o.yyy        // "function"    <- an object literal is fine
```

A *declared* `any` field behaves the same way (`class A { hook: any }`,
`a.hook = fn`, `a.hook` → `undefined`), while a non-function expando works
(`a.zzz = 7; a.zzz` → `7`). This is exactly how Node's `test-v8-serdes.js`
installs the serializer hooks (`ser._writeHostObject = fn`), so that spelling
cannot work here; `Serializer`'s hooks are therefore *called* as methods
(`owner._writeHostObject(v)`), which does find a subclass override, and the
whole serializer state lives in one plain-object field. Related to zun#19
(class methods as values) and zun#37 (expando write through `any`), but the
case above is a *write* of a function onto an instance rather than a read of a
declared method.

### 3. A module-level `const x: DataView` is not a `DataView` inside a function (looks new)

```ts
const topDv: DataView = new DataView(new ArrayBuffer(8));

function useTop(): string {
  topDv.setFloat64(0, 1.5, true);   // TypeError: setFloat64 is not a function
  return "";
}

function useLocal(): string {
  const dv: DataView = new DataView(new ArrayBuffer(8));
  dv.setFloat64(0, 1.5, true);      // works
  return String(dv.getUint8(7));    // "63"
}

function dvOf(): DataView { return topDv; }
const d: DataView = dvOf();
d.setFloat64(0, 1.5, true);         // works again
```

So the value is fine and the *binding* is what degrades. The workaround in
`src/v8/v8.ts` is the third form: the scratch view is handed out by
`__v8ScratchView()`, a function with a declared `DataView` return type. Same
family as zun#34 (a top-level binding invisible to functions), for a nominal
engine type rather than a destructuring.

## Shapes that differ from Node, and why

* **`new v8.Serializer()` without `new`.** Node throws
  `ERR_CONSTRUCT_CALL_REQUIRED`. There is no function-constructor model here
  (zun#25), so a plain call is simply a call.
* **`Buffer` versus `Uint8Array` on the wire.** They are one runtime type in
  this engine, so both serialize as view-type index 10 (`FastBuffer`). Node
  writes 1 for a `Uint8Array`. Index 10 is the choice because it makes the
  common case — a `Buffer` — byte-identical.
* **boxed primitives.** `new Number(3.5)`, `new String('x')` and
  `new Boolean(true)` have no wrapper-object form here, so `kNumberObject`,
  `kStringObject` and `kTrueObject`/`kFalseObject` are *read* back as the
  primitive and are never written.
* **holes.** A sparse array deserializes with `undefined` in the gaps rather
  than with holes: there is no way to create a hole. `Object.keys` therefore
  reports more keys than Node's would for such an array.
* **`BigInt64Array` / `BigUint64Array` / `Float16Array`.**
  `new BigInt64Array([42n])[0]` answers `0` here and `Float16Array` is not
  defined at all, so those three view-type indices are rejected on read with
  the reason named instead of returning a view full of zeros.
* **`writeHeapSnapshot`, `queryObjects`, `promiseHooks`.** Each throws with
  its reason. An empty heap graph is an honest *snapshot* (the format is
  valid and the graph is what this runtime exposes: nothing), but a *count* of
  live instances, a file path to a file that was never written and a promise
  hook that never fires would each be a wrong answer rather than an empty one.
