# Node.js v25 `domain` corpus

The bar for `node:domain` is Node's own `test/parallel/test-domain-*.js` — 50
files at `v25.0.0`, listed in [`NODE_TESTS.txt`](NODE_TESTS.txt). The per-test
result, with the first line of each failing run's stderr, is in
[`RESULTS.md`](RESULTS.md), regenerated by

```sh
bash zun-node/tools/run_node_tests.sh --zun target/release/zun   --ext zun-node/target/debug/libzun_node.so --module domain
```

`domain` is bookkeeping over `events`, `process.nextTick` and `timers`, with no
syscall anywhere in it, so nothing in `src/domain/` imports a native. The
tracker kind is nevertheless **`zun-ts+ext`**, for the same reason `readline`'s
is: four files in the corpus require a module that *is* syscalls
(`test-domain-implicit-fs`, `-implicit-binding` and `-fs-enoent-stream` require
`fs`, `-crypto` requires `crypto`), and without `--ext` those bundles fail to
compile rather than failing on their real blocker. Each test is bundled by
`tools/bundle_node_test.sh` — which inlines `src/domain/domain.ts` only for a
test that actually requires it — and run as `zun run --ext <lib> <bundle.ts>`.

## How the module reaches into the other three

Node's `lib/domain.js` is a monkey-patch: it replaces `EventEmitter.init` and
`EventEmitter.prototype.emit`, replaces
`process.setUncaughtExceptionCaptureCallback`, redefines `process.domain` as an
accessor, and registers an `async_hooks` hook so that every callback re-enters
the domain that created it. None of that is expressible here — there is no
prototype model to patch ([zun#25](https://github.com/UrubuCode/zun/issues/25)),
a class method cannot be read as a value
([zun#19](https://github.com/UrubuCode/zun/issues/19)), and the VM has no
async-hooks tier at all.

So the direction is inverted. `src/events/events.ts` declares one record,
`__domainHooks`, whose every slot is `null`, and `src/domain/domain.ts` is its
only writer; `events`, `process` and `timers` consult it at exactly the points
Node patches:

| Node | Here |
|---|---|
| patched `EventEmitter.init` | `__domainHooks.init`, called from `EventEmitter`'s constructor and `init()` |
| patched `EventEmitter.prototype.emit` | `__domainHooks.emit`, called from `EventEmitter.emit` ahead of `__evEmit` |
| `async_hooks` `init` + `before`/`after` | `__domainHooks.active` is stamped onto each `nextTick` entry and onto each `Timeout`/`Immediate` (`_domain`); `__domainHooks.callback` then runs the callback inside that domain |
| `process._fatalException` → the capture callback | `__processUncaught.callback`, which `src/process/process.ts` already consults ahead of `process.on('uncaughtException')` in Node's order |
| patched `process.setUncaughtExceptionCaptureCallback` | `__domainHooks.blockCapture` |

With no `domain` in the bundle every slot stays `null`, so the whole cost to
every other corpus is one null check per emit, per constructed emitter, per
tick and per timer fire. Two properties are permanent, because Node's own tests
read them off a *statically typed* receiver and a field no class declares is a
compile error here: `EventEmitter.domain` (`null` by default, as in Node) and
`Timeout._domain`/`Immediate._domain`. They are enumerable where Node's are
not — see the deviations below.

`process.emit` is deliberately left out: it calls `__evEmit` directly rather
than the class method, which is exactly Node's `this === process` exclusion.

## The shape of the corpus

Twenty-two of these fifty files are not about the domain bookkeeping at all.
**Fifteen spawn a child process of the engine itself** to observe an exit code,
a signal or a `process.send` message under `--abort-on-uncaught-exception`: the
ten `test-domain-no-error-handler-abort-on-uncaught-{0..9}` (which call
`common.childShouldThrowAndAbort()`), `-with-abort-on-uncaught-exception`,
`-top-level-error-handler-throw`, `-uncaught-exception`, `-nested-throw` and
`-throw-error-then-throw-from-uncaught-exception-handler`. **Five need a module
this library does not have** — `net` (`-abort-on-uncaught`), `http`
(`-http-server`, `-multi`), `inspector` (`-dep0097`) and `vm`
(`-vm-promise-isolation`). `-promise` needs `vm` *and* the async-hooks tier,
and `-async-id-map-leak` needs `async_hooks.AsyncResource` plus `--expose-gc`.

The remaining twenty-eight are the module itself — the stack, the implicit
binding, `run`/`bind`/`intercept`, the error decoration and the routing of a
throw out of a tick, a timer, an immediate and an fs callback — and **eighteen
of those pass**, including every file that pins the stack discipline
(`-enter-exit`, `-safe-exit`, `-stack`, `-nested`,
`-thrown-error-handler-stack`, `-top-level-error-handler-clears-stack`,
`-stack-empty-in-process-uncaughtexception`). The ten that do not are one
engine gap each; the table below names them.

### One pass that is counted and should not be trusted

`test-domain-stack.js` exits 0 and the tracker scores it green, but its own
assertion never runs. The file queues **1000** `process.nextTick(d.bind(fn))`
calls and checks `domain._stack.length > 5` inside the domain's error handler;
past roughly 300 ticks the handler's read of the test's own top-level
`const domain` answers `undefined`, so every later invocation dies with
`TypeError: Cannot read properties of undefined (reading '_stack')` instead of
checking anything. The throws are then swallowed by the error-handler recursion
and the run still exits 0.

This is **not** a `domain` defect: the same shape fails identically on `main`
with no `domain` in the bundle at all —

```js
// bundled as a Node test and run with zun: prints two TypeErrors, exits 0
const st = { n: 0 };
function tick() {
  try { throw new Error('boom'); } catch (e) { st.n = st.n + 1; }
}
for (let i = 0; i < 1000; i++) process.nextTick(tick);
process.nextTick(function () { process._rawDebug('after ticks n=' + String(st.n)); });
```

— and bisecting the loop count puts the threshold between 200 (works) and 400
(fails). It does not reproduce in a small standalone program: `queueMicrotask`
driving 10 000 allocating callbacks, 2000 `new Error`s inside a `try`, or a
hand-written copy of `src/process/process.ts`' tick queue (entry objects,
`shift()`, a boxed callable) all answer correctly. So the trigger needs the
whole bundle's heap, which is what makes the diagnosis most likely to be
**GC rooting**: a module-level `const` object lives in the main script's frame,
and `crates/zun_interp/src/lib.rs`' `poll_gc` is documented as treating "the
current frame plus the ancestor root chain" as the live set — once the main
script has returned, a tick callback's frame has no such ancestor, so a
module-level binding read from inside one can be collected. Recorded here
rather than as a `domain` blocker because it affects any corpus whose test body
keeps state in a top-level object and touches it from a few hundred ticks.

## Deviations from Node that are not test failures

These are places where this module is knowingly not Node, written down so that
nobody reads a pass as proof of the opposite.

1. **A throw out of `run`/`bind`/`intercept` is caught here.** In Node the
   exception leaves `d.run(fn)` and only reaches the domain if nothing catches
   it on the way to `process._fatalException`. This engine has no
   uncaught-exception hook — an error that escapes the main script ends the
   program before any JavaScript sees it, which is why
   `src/process/process.ts` documents
   `setUncaughtExceptionCaptureCallback` as best effort — so `run` and the two
   wrappers route the error themselves, through the same
   `__processReportUncaught` path a tick or timer throw takes. For the shape
   every domain test is written in, that is exactly Node's outcome; it deviates
   only for `try { d.run(f) } catch {}`, where Node never consults the domain
   and this does.
2. **`EventEmitter.domain` and `Timeout._domain` are enumerable.** Node's are
   own properties defined with `enumerable: false`; here they are declared
   class fields, because `Object.defineProperty` on a class instance poisons
   every later typed read of that instance's own fields (zun#37 —
   `Timeout.unref()`'s `this._refed` is the repro) and because Node's tests
   read `e.domain` off a statically typed emitter. `err.domain` *is* defined
   non-enumerably, as in Node.
3. **`d.bind(cb)`'s result carries no `domain` property.** A function loses its
   own properties when it crosses the `Any` lane
   ([zun#50](https://github.com/UrubuCode/zun/issues/50)), and the wrapper has
   to cross it to be returned from a class method at all.
4. **A *function* thrown into a domain is not decorated.** `Object.*`
   reflection aborts the program when its target is a function
   ([zun#49](https://github.com/UrubuCode/zun/issues/49)), so
   `__domDecorable` accepts only non-null objects. Node's decoration of a
   thrown function is unobservable through this corpus.
5. **`Domain.prototype.dispose` is absent**, as it is in Node 25 — it was
   removed from `lib/domain.js` long ago.
6. **No receiver is threaded into a `run`/`bind`/`intercept` callback.** Node's
   `ReflectApply(fn, this, …)` makes the domain the receiver;
   `apply`/`call`/`bind` thread no receiver here
   ([zun#1](https://github.com/UrubuCode/zun/issues/1)). No file in the corpus
   reads `this` inside one of those callbacks.
7. **`err.stack` is not extended** with the `require('domain')` stack on
   `ERR_DOMAIN_CANNOT_SET_UNCAUGHT_EXCEPTION_CAPTURE`:
   `Error.prototype.stack` cannot be assigned
   ([zun#74](https://github.com/UrubuCode/zun/issues/74)).

## Engine bugs this module found

### `Error`'s `name` and `stack` become unreadable once the error carries any own property

Reported here because it is the blocker behind `test-domain-implicit-fs` and
because it makes `util.inspect(err)` throw for *any* error decorated the way
Node's own code decorates one (`err.code = …`, `err.domain = …`).
[zun#37](https://github.com/UrubuCode/zun/issues/37) covers the *typed* read
path and its latest comment states that the same field read through an `any`
alias still works; this is the opposite — the read is through an `any`, the
member is `Error`'s own `name`/`stack`, and it throws.

```ts
// zun run r.ts
function set(o: any, k: string, v: any): void { o[k] = v; }
function read(o: any, k: string): any { return o[k]; }
const e: any = new Error("m");
console.log(read(e, "name"));          // Error
set(e, "x", 1);                        // the expando Node's own code writes
console.log(read(e, "message"));       // m        (still fine)
console.log(read(e, "name"));          // TypeError: Cannot read private member
                                       //   from an object whose class did not
                                       //   declare it
```

`node r.js` prints `Error`, `m`, `Error`. A *user* class behaves correctly — a
declared field and a getter both survive the same expando — so the fault is
specific to the built-in `Error`'s members. Code site:
`crates/zun_interp/src/lib.rs`' `Opcode::LoadField`, which throws this exact
message when `h.is_dynamic_object(obj)`; the expando write switches the error
to the dynamic layout and the `name`/`stack` reads are still lowered to a fixed
`LoadField`. The practical consequence is that `console.error(err)` dies for
every error any Node-style code has annotated.

### `Error.stackTraceLimit = Infinity` panics the interpreter

Two lines, no library involved:

```ts
Error.stackTraceLimit = Infinity;
console.log("ok");
```

```
thread '<unnamed>' panicked at crates\zun_interp\src\value.rs:226:25:
expected object, found Any(Any { tag: ClassDescriptor, payload: 30 })
```

`node` prints `ok Infinity`. This is
[zun#20](https://github.com/UrubuCode/zun/issues/20)'s "assigning to a class
panics", landing on a built-in; it is recorded here because
`test-domain-set-uncaught-exception-capture-after-load` opens with that exact
line, and because a panic is a worse failure mode than a `TypeError`. Reading
it answers `undefined` rather than `10`.

### No `Function` global

`typeof Function` is `"undefined"` and any use is
`ReferenceError: Function is not defined`, so the idiom Node's tests use for a
receiver-bound built-in —
`Function.call.bind(Object.prototype.propertyIsEnumerable)` — cannot be
written. It is the sole blocker of three files in this corpus.
[zun#25](https://github.com/UrubuCode/zun/issues/25) covers the missing
function-constructor *model* (`new F()`, `F.prototype`); the global binding
itself is not mentioned there. `Object.prototype`'s members are unreadable as
well ([zun#5](https://github.com/UrubuCode/zun/issues/5)), and
`obj.propertyIsEnumerable(k)` answers `false` for every key including an
enumerable one, so all three would have to be fixed for those files to move.
