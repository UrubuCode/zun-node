# `node:perf_hooks` against Node.js v25's own tests

Corpus: `nodejs/node@v25.0.0` `test/parallel/test-perf-hooks-*` and
`test/parallel/test-performance*` — 20 files, listed in
[`NODE_TESTS.txt`](NODE_TESTS.txt). The per-test run is
[`RESULTS.md`](RESULTS.md), regenerated by

```sh
bash tools/run_node_tests.sh --zun <path/to/zun> --module perf_hooks
```

The module is `src/perf_hooks/perf_hooks.ts`, pure Zun TypeScript over the one
capability it does not own — a clock, which `src/process/process.ts` already
answers through `process.hrtime`. Its tracker kind is therefore `zun-ts`; see
the resolution table at the top of that file for what `--ext` buys (nanoseconds
instead of whole milliseconds) and why no test in this corpus needs it.

## What is implemented

The whole documented surface, so that a blocker below is a blocker in the
engine rather than a gap in the module:

- `performance`: `now`, `timeOrigin`, `mark`, `measure` (all six
  start/end/duration resolutions, `detail`, `startTime`), `getEntries`,
  `getEntriesByName`, `getEntriesByType`, `clearMarks`, `clearMeasures`,
  `clearResourceTimings`, `setResourceTimingBufferSize`, `markResourceTiming`,
  `toJSON`, `timerify`, `eventLoopUtilization`, `nodeTiming`, and the
  `EventTarget` half (`addEventListener` / `removeEventListener` /
  `dispatchEvent`, which is how `resourcetimingbufferfull` is delivered).
- `PerformanceEntry`, `PerformanceMark`, `PerformanceMeasure`,
  `PerformanceResourceTiming`, `PerformanceObserver` (+ `takeRecords`,
  `supportedEntryTypes`, buffered single-type observation, the
  single-versus-multiple observation lock), `PerformanceObserverEntryList`,
  `PerformanceNodeTiming`.
- `createHistogram` / `RecordableHistogram`, `monitorEventLoopDelay` /
  `IntervalHistogram`: `min`, `max`, `mean`, `stddev`, `count`, `exceeds`,
  `percentile`, `percentiles`, the five `*BigInt` variants, `record`,
  `recordDelta`, `add`, `reset`, `enable`, `disable`.
- `constants`.
- The three global entry buffers with Node's ordering, the resource-timing
  secondary buffer and its single `resourcetimingbufferfull` drain, and the
  million-entry `MaxPerformanceEntryBufferExceededWarning`.

Two of the corpus files were re-run with **only** their
`Object.getOwnPropertyDescriptor(…, Symbol.toStringTag)` block removed, to
separate that one engine gap from everything behind it:

| File | with the descriptor block | without it |
|---|---|---|
| `test-perf-hooks-usertiming.js` | fails on the descriptor | **passes in full** — every `mark`/`measure`/`detail`/`getEntriesBy*` assertion in the file |
| `test-perf-hooks-resourcetiming.js` | fails on the descriptor | reaches the last assertion; the only remaining difference is the *indentation* `util.inspect` gives a class instance nested in an array (two spaces instead of four) |

## Verification: a differential run against Node

Most of what this module implements is never reached by the corpus — every
histogram reading, `monitorEventLoopDelay`, `timerify`'s histogram and
rethrow paths, and most of the `ERR_*` edges are behind a file that is blocked
before its first assertion. So the module is verified the way `os`,
`string_decoder` and `url` are: one program run under `node` and under `zun`,
and the two outputs diffed. **68 scenarios, one divergence** — and the
divergence is not in this module:

* every histogram reading on an empty, a one-value and a three-value histogram
  (`min`/`max`/`mean`/`stddev`/`count`/`exceeds`, the five `*BigInt`
  variants, `percentile`, and the full `percentiles` map, whose halving-level
  iteration is HdrHistogram's and not "one entry per value" — see the comment
  at `__perfHistogramPercentiles`), `record` with a number and with a BigInt,
  `recordDelta`, `add`, `reset`, `exceeds` past `highest`, and every
  `createHistogram`/`record`/`percentile` validation error;
* `monitorEventLoopDelay`'s `enable`/`disable` idempotence and its two option
  errors;
* `timerify`'s return value, its rethrow, its two argument errors and the
  histogram it records into;
* `PerformanceObserver.supportedEntryTypes`, `takeRecords`, and the five ways
  `observe` rejects its options (including the two `DOMException`s, matched on
  the legacy numeric `code` Node's carries);
* `mark`/`measure`'s nine error edges, `detail` structured cloning,
  `duration`-option resolution, `getEntries*` ordering across the three
  buffers, `toJSON`, `nodeTiming`'s keys, `eventLoopUtilization` and
  `constants`.

The one divergence: `util.inspect` of a large integer. Node writes
`9_007_199_254_740_992` with digit separators and `src/util/util.ts` writes
`9007199254740992`, so an `ERR_OUT_OF_RANGE` message that quotes such a number
differs by those underscores. That is a `util` gap shared by every module that
raises the error, not a `perf_hooks` one, and it is left to `util`.

## Deviations from Node, and why

- **`nodeTiming`'s milestones.** `nodeStart`, `v8Start`, `environment` are 0 and
  `bootstrapComplete` is the instant this module finished loading; `loopStart`
  and `loopExit` are `-1` and `idleTime` is 0. The VM publishes no process
  milestone and no loop edge to managed code, and `-1` is exactly Node's own
  value for a loop that has not started or exited — which is also what makes
  `eventLoopUtilization()` answer `{ idle: 0, active: 0, utilization: 0 }`, the
  reading `test-performance-eventlooputil.js` expects on a main thread before
  the loop starts. Fabricating four increasing numbers would turn one honest
  gap into four wrong answers.
- **`performance.now()` reads wall time, not the VM's virtual clock.** Node's
  `now()` is the same monotonic clock libuv arms timers with. Here the two are
  different clocks, and the virtual one is not exposed, so a duration measured
  across a `setTimeout` is ~0 rather than the delay. This is the single reason
  `test-performance-measure.js` does not really pass.
- **An exact histogram instead of HdrHistogram**, and **`timerify` without the
  constructor path** — both are explained at the top of
  `src/perf_hooks/perf_hooks.ts`.
- **Entries carry their readings as fields, not accessors.** Node's entries are
  read-only accessors with a `[util.inspect.custom]` method; neither spelling
  survives here (the reasons are at the entry classes in the source), so the
  fields are named and ordered so that the engine's own formatting *is* Node's
  `[kInspect]` output. `PerformanceResourceTiming`'s derived readings are
  therefore computed when the entry is created rather than on every read, which
  nothing can observe — the timing info is final by then.

## New engine findings

Minimal repros are in the scratch directory for this track; each was checked
against the open **and** closed issue list.

1. **A BigInt loses identity across a value round-trip.** `===` against a
   literal is `true` only when both sides fold at compile time.

   ```ts
   function id(x: any): any { return x; }
   console.log(id(BigInt("5")) === 5n);     // zun: false   node: true
   console.log(BigInt("5") === 5n);         // zun: true    node: true  (folded)
   ```

   Related but distinct: [zun#86](https://github.com/UrubuCode/zun/issues/86)
   (a `bigint`-typed class *field* reads back `undefined`),
   [zun#42](https://github.com/UrubuCode/zun/issues/42) (a BigInt enumerates as
   another class), [zun#23](https://github.com/UrubuCode/zun/issues/23) (closed,
   the same gap for symbols).

2. **`writable: false` is not stored for a symbol-keyed property**, while the
   same descriptor with a string key round-trips.

   ```ts
   const o: any = {};
   const k: any = Symbol("k");
   Object.defineProperty(o, k, { configurable: true, enumerable: false, writable: false, value: 1 });
   console.log(Object.getOwnPropertyDescriptor(o, k).writable);   // zun: true    node: false
   Object.defineProperty(o, "s", { configurable: true, enumerable: false, writable: false, value: 1 });
   console.log(Object.getOwnPropertyDescriptor(o, "s").writable); // zun: false   node: false
   ```

   This is the whole blocker for two corpus files, and the pattern it breaks —
   `ObjectDefineProperties(C.prototype, { [SymbolToStringTag]: { … } })` — is on
   every web-platform class Node ships. Nearest existing issues:
   [zun#32](https://github.com/UrubuCode/zun/issues/32) (function-valued
   properties in a side store, droppable under a symbol key),
   [zun#80](https://github.com/UrubuCode/zun/issues/80) (`Object.hasOwn` and
   accessors).

3. **Class-instance allocation is quadratic in the number of live class
   instances**; object-literal allocation is flat.

   ```ts
   class E { n: any = 0; constructor(n: any) { this.n = n; } }
   const live: any[] = [];
   for (let r = 0; r < 4; r++) {
     const t0: number = Number(Date.now());
     for (let i = 0; i < 50000; i++) live.push(new E(i));
     console.log(String(Number(live.length)) + " live: " + String(Number(Date.now()) - t0) + "ms");
   }
   // zun:  50000 live: 137ms   100000: 221ms   150000: 303ms   200000: 333ms
   // zun, with `{ n: i }` instead of `new E(i)`: 122ms, 118ms, 140ms, 93ms
   // node: 7ms, 3ms, 3ms, 1ms
   ```

   Inside a bundle (28 000 lines of library ahead of the test) the constant is
   far worse: 20 000 `performance.mark()` calls take 2.6 s and 100 000 take
   25 s. Related in spirit only:
   [zun#12](https://github.com/UrubuCode/zun/issues/12) (quadratic string
   scans), [zun#67](https://github.com/UrubuCode/zun/issues/67) (GC root chain).

4. **An exception thrown inside a macrotask does not fail the run.** The error
   is printed and the process still exits 0, so any test whose assertions live
   in a `setImmediate`/`setTimeout`/observer callback can pass spuriously —
   across every corpus, not just this one.

   ```ts
   setImmediate(function (): void { throw new Error("should fail the run"); });
   // zun: prints the error, exit 0        node: prints the error, exit 1
   ```

   Nearest existing issue:
   [zun#8](https://github.com/UrubuCode/zun/issues/8) (an uncaught exception
   prints only an address) — the same path, but that one is about the *message*,
   not the exit code.

5. **A spread into a method call is lowered at top level but not inside a
   function body.** A spread into a *free function* inside a function body
   works, so it is specific to the method path.

   ```ts
   class K { mr(...a: any[]): number { return Number(a.length); } }
   const k: K = new K();
   const sp: any[] = [1, 2, 3];
   function freeFn(...a: any[]): number { return Number(a.length); }
   console.log(k.mr(...sp));                                       // ok
   function insideFree(): number { return freeFn(...sp); }         // ok
   function insideMethod(): number { return k.mr(...sp); }         // error: [SEM0001] spread arguments are not lowered yet
   ```

   [zun#15](https://github.com/UrubuCode/zun/issues/15) is closed and covered
   two different shapes (an `any` operand, and a callee that is a captured
   closure parameter); this is a third.

## Engine behavior this module had to work around

Each is marked at its use site in `src/perf_hooks/perf_hooks.ts`.

| Behavior | Where it bites |
|---|---|
| The prelude's `performance.now()` is lowered to the prelude *even when a user declaration shadows it* — the `console` problem ([zun#85](https://github.com/UrubuCode/zun/issues/85)) for a second global | the module binds `__zunPerformance` and `tools/bundle_node_test.sh` rewrites `performance` as a receiver, exactly as it does `console` |
| A method called with **eight** arguments does not compile through an `any` receiver ([zun#10](https://github.com/UrubuCode/zun/issues/10)) | `performance` is declared with its class type, not `any`; `markResourceTiming` takes a rest parameter |
| A method read **as a value** is `undefined` through an `any` receiver ([zun#19](https://github.com/UrubuCode/zun/issues/19)) | the same; `assert(performance.mark)` is in the corpus |
| `structuredClone` rejects a RegExp ("unsupported object kind") where Node's clones it | `detail` is cloned by `__perfClone` |
| `Promise` has no readable fields at the type level and no `finally` | `timerify`'s promise path detects a thenable through an `any` alias and chains with `then` |
| BigInt arithmetic is unavailable ("Cannot convert a BigInt value to a number") | every `*BigInt` reading is computed as a number and converted once through decimal text |
| `arguments.length` counts declared parameters, not supplied ones | every method that owes `ERR_MISSING_ARGS` takes a rest parameter and counts it |
| An undeclared property read off a **string** held in an `any` panics the interpreter | `measure('x', 'markName')` reaches `options?.detail` with a string; `__perfDetailOf` takes the non-object cases first |
| A symbol-keyed function property is dropped on a class instance ([zun#32](https://github.com/UrubuCode/zun/issues/32)) and `Object.defineProperty` with a function value reads back `undefined` ([zun#48](https://github.com/UrubuCode/zun/issues/48)) | no `[util.inspect.custom]` hook; the entry fields are named and ordered to make the engine's own formatting Node's output |
| `ERR_ILLEGAL_CONSTRUCTOR` is already a top-level name in `src/stream/stream.ts` | the class here is named `__PerfIllegalConstructor`; only its `code` and message are Node's |
