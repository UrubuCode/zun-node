# node:path — Node.js compatibility tests

The compatibility bar for `path` is **Node.js 25's own test suite**, not tests we
write. `path` is **not finished** until it passes 100% of Node's `test-path*`
tests.

## The oracle

`NODE_TESTS.txt` is the full inventory of Node 25's `test/parallel/test-path*.js`
files — 17 of them, including `test-path.js` itself (which is why the tracker
matches the prefix `test-path`, not `test-path-`):

```
test-path.js                               test-path-parse-format.js
test-path-basename.js                      test-path-posix-exists.js
test-path-dirname.js                       test-path-posix-relative-on-windows.js
test-path-extname.js                       test-path-relative.js
test-path-glob.js                          test-path-resolve.js
test-path-isabsolute.js                    test-path-win32-exists.js
test-path-join.js                          test-path-win32-normalize-device-names.js
test-path-makelong.js                      test-path-zero-length-strings.js
test-path-normalize.js
```

Each is fetched verbatim from `nodejs/node` at tag `v25.0.0`; nothing is vendored
here. Unlike `fs`, these tests need no `test/fixtures/` tree: they only compute
over strings.

## How they run

`path` is **not** a `zun_abi` extension. It is pure string computation, so it is
written in Zun TypeScript (`../../src/path/path.ts`) and compiled by the
platform's own compiler — no `--ext` library, no syscalls. See `../../PLAN.md`.

Node's tests are CommonJS (`require('path')`, `require('assert')`,
`require('../common')`) and the Zun engine has no `require` and no file-based
module resolution ([zun#4](https://github.com/UrubuCode/zun/issues/4)). The
bundler bridges that gap:

```sh
tools/bundle_node_test.sh <node-test.js> <out.ts>   # inline + rewrite
zun run <out.ts>                                    # run the bundle
```

`tools/bundle_node_test.sh` concatenates, in order,
`src/process/process.ts`, `src/assert/assert.ts`, `src/path/path.ts` and
`tools/harness/common.ts` ahead of the test body, injects `__filename` /
`__dirname`, then rewrites the test's `require` lines: a whole-line
`const path = require('path');` is deleted (the inlined module already binds the
name `path`) and inline forms such as `require('path/win32')` are replaced by the
corresponding binding. Any surviving `require(` is reported loudly, so a missing
harness module never shows up as a mystery engine error.

The `assert` and `process` slices exist for exactly this reason: Node's path
tests need them, and PLAN.md principle 4 says to implement just the piece that
unblocks the module in hand.

The tracker drives both steps:

```sh
bash tools/run_node_tests.sh --zun <path-to-zun> --module path
```

Tests are downloaded into `<tmp>/test/parallel/<name>` because several of them
assert their own location through `__dirname`.

## Status and what blocks the rest

[`RESULTS.md`](RESULTS.md) is the live per-test table, with the first line of
stderr for each failure; it and the README bar are regenerated by every tracker
run, so they — not this page — are the current number.

Everything still failing is blocked in the **engine** (and, for one block, the
harness), not in `path.ts`: differential runs against Node over every string in the
corpus plus generated root/tail combinations (about 36 000 assertions, both
namespaces, every function) show **zero divergences**, including the 186 `join` and
24 `resolve` expectations extracted from those two test files. The cases, as measured
on Windows:

| Test | Blocked by | What happens |
|---|---|---|
| `test-path-join.js` | [zun#17](https://github.com/UrubuCode/zun/issues/17) | two faces of the same issue, both in the driver rather than in `path.ts`. The table is walked as `test[0].forEach((join) => … join.apply(null, test[0]))`, and a function taken out of an array is a `functionBox` record with no `apply` on it — `join.apply` throws `apply is not a function`. The failure message then uses `test[0].map(JSON.stringify)`, a built-in read as a value, which aborts the VM with `call did not resolve to a method`. Two blockers this test used to have are gone: [zun#16](https://github.com/UrubuCode/zun/issues/16) is closed, so `joinTests[0][1].slice(0).concat([…])` builds the 3-row Windows table correctly, and `join === path.win32.join` holds for a function stored in an array (#17's identity half). The spread spelling `join(...test[0])` works, so the file is one `apply` away. |
| `test-path-resolve.js` | [zun#17](https://github.com/UrubuCode/zun/issues/17); harness: `child_process` | the same driver shape as `join`, minus the `concat`. Its Windows-only tail spawns `process.argv[0]` on `test/fixtures/path-resolve.js` through `child_process.spawnSync`, which the harness only stubs — it needs a real `child_process`, which belongs to that module's own work. On Linux the other branch (`process.cwd = () => ''`) runs instead. |

`test-path-parse-format.js` **passes now.** It was the one file blocked by
[zun#14](https://github.com/UrubuCode/zun/issues/14) — `checkParseFormat` uses
the bare `assert(output.dir.startsWith(output.root))` form, which needs a value
that is callable *and* carries `strictEqual` & co. A function can carry callable
properties now, and they resolve from module scope, from a nested function, from
a closure and through an `any` parameter, so `src/assert/assert.ts` is a real
function with the methods attached — the shape `lib/assert.js` exports
(`module.exports = assert = ok`).

Uncaught errors are printed as `Object(Obj(0x…))`
([zun#8](https://github.com/UrubuCode/zun/issues/8)), which is why the "Why" column
in `RESULTS.md` is often opaque; `assert` prints the failure to stderr before
throwing to compensate.

Other engine issues that `path.ts` works around (no test is blocked by them):
[#2](https://github.com/UrubuCode/zun/issues/2) `charCodeAt` out of range,
[#3](https://github.com/UrubuCode/zun/issues/3) `.length` is still typed `u64` by
the checker (its *arithmetic* was widened, so `len - 1` and the descending
`for` loop are correct now, but `.length` can be neither assigned to nor passed
as a `number` — which is why `slen()`/`alen()`/`indexOfChar()` stay),
[#7](https://github.com/UrubuCode/zun/issues/7) RegExp through `any`,
[#13](https://github.com/UrubuCode/zun/issues/13) `!x` on an `any` empty string.

All four were re-probed against this engine build and all four still hold — and
#2 and #3 only hold **in typed code**, which is exactly where `path.ts` lives.
Through an `any` lane, `s.charCodeAt(99)` answers `NaN` and `s.length` passes as
a `number`; in a typed function, `value.charCodeAt(99)` is still an uncatchable
`charCodeAt: index 99 is out of bounds` abort and `takesNumber(value.length)` is
still rejected with ``argument type Int(IntKind { bits: 64, signed: false })
does not match Float(F64)``. Probing either one through `any` reports them fixed
when they are not, the same trap #13's note describes.

[#9](https://github.com/UrubuCode/zun/issues/9) — a string literal truncated at
an embedded `U+0000` — is **fixed**, in typed code as well as through `any`:
`"a\u0000b".length` is 3, `charCodeAt(1)` is 0, and `indexOf`, `slice`, `split`,
concatenation and `String.fromCharCode(0)` all round-trip. It was never worked
around here; it was what used to keep
`test-path-win32-normalize-device-names.js`'s reserved-device inputs from being
read as written.

A note on probing #13, because it is easy to call fixed and is not:
`const x: any = ""` is constant-folded to a static string, so `!x` answers
correctly there. The bug shows as soon as the empty string arrives from a
property read, a parameter or another `any` binding — `!value` is `false` and
`Boolean(value)` is `true` while `?:` is right — which is every use site in
`path.ts`, so `truthy()` stays.

[#37](https://github.com/UrubuCode/zun/issues/37) is not worked around — it is
designed out. `path.ts` raises `ERR_INVALID_ARG_TYPE` as a `NodeTypeError`, a
real `TypeError` subclass with `code` as a **declared** field, because the
expando spelling (`const e: any = new TypeError(m); e.code = '…'`) poisons the
instance and makes every later statically typed read of its own members throw,
`e.name` included. `test-path.js` reads exactly that field, in
`assert.throws(fn, { code, name })`, for all 160 of its expectations.

Two further issues limit what callers can do:
[#10](https://github.com/UrubuCode/zun/issues/10) (`path.join` with 7+ arguments
does not compile, because the namespaces are object literals) and
[#12](https://github.com/UrubuCode/zun/issues/12) (`charCodeAt`/`slice` are
O(n), so every path API is O(n²) on long inputs).

### Platform note

`test-path-win32-normalize-device-names.js` is Windows-only: on any other
platform it calls `common.skip`, which the harness turns into exit 0, so the
Linux CI runner scores it as a pass. It is only a real signal when the tracker
runs on Windows — where it does currently pass.
