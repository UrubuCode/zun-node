# node:querystring — Node.js compatibility tests

The compatibility bar for `querystring` is **Node.js 25's own test suite**, not
tests we write. `querystring` is **not finished** until it passes 100% of Node's
`test-querystring*` tests.

## The oracle

`NODE_TESTS.txt` is the full inventory of Node 25's
`test/parallel/test-querystring*.js` files — four of them, including
`test-querystring.js` itself (which is why the tracker matches the prefix
`test-querystring`, not `test-querystring-`):

```
test-querystring.js                        test-querystring-maxKeys-non-finite.js
test-querystring-escape.js                 test-querystring-multichar-separator.js
```

Each is fetched verbatim from `nodejs/node` at tag `v25.0.0`; nothing is
vendored here. They need no `test/fixtures/` tree: they only compute over
strings.

## How they run

`querystring` is **not** a `zun_abi` extension. It is pure string computation,
so it is written in Zun TypeScript (`../../src/querystring/querystring.ts`) and
compiled by the platform's own compiler — no `--ext` library, no syscalls. See
`../../PLAN.md`.

```sh
bash tools/run_node_tests.sh --zun <path-to-zun> --module querystring
```

The tracker bundles each test with `tools/bundle_node_test.sh` (which rewrites
`require('querystring')` to the single object `__node_querystring`) and runs the
bundle as `zun run <bundle.ts>`.

### The `__proto__` key

Node keeps `parse`'s result null-prototype precisely so that a `__proto__` key
is an ordinary own property, and `test-querystring.js` asserts it with
`['__proto__=1', '__proto__=1', createWithNoPrototype([{ key: '__proto__', value: '1' }])]`.
On this engine a plain `obj["__proto__"] = value` assignment is treated as a
prototype *set* even when the object has a null prototype, so the own property
is silently lost — `Object.keys` comes back empty and the read answers
`undefined` — [zun#47](https://github.com/UrubuCode/zun/issues/47).
`querystring.ts` works around it with `Object.defineProperty` for that one key
(`__qsSetKey`/`__qsGetKey`), which does create the own property, so
`qs.parse('__proto__=1')` is correct here; the test's own
`createWithNoPrototype` helper, written in the test body, still loses it.

### Why the scanner looks different from Node's

The algorithm is Node's, position for position. The *addressing* is not:
`charCodeAt(index)` and `slice(from, to)` are O(n) in the string's length
([zun#12](https://github.com/UrubuCode/zun/issues/12)), which turns Node's
single-pass `for (i = 0; i < qs.length; i++)` loop into an O(n²) one — measured
on this engine, scanning 16 000 characters that way takes 23 seconds. Every scan
in `querystring.ts` therefore runs over the code-unit array `split("")` produces,
which is linear and cheap. `test-querystring-maxKeys-non-finite.js` parses a
98 kB query string four times and is the test that makes this mandatory; it
passes in about eight seconds.

### `unescapeBuffer` without `node:buffer`

Node's `unescapeBuffer` answers a `Buffer`. `node:buffer` is not implemented yet
(it is its own module in `../../PLAN.md`'s roadmap), so the value handed back is
the closest honest thing: an array-like object carrying one byte per index, a
`length`, and a `toString()` that decodes those bytes as UTF-8. That is exactly
the surface Node's own tests use on it (`b[0] … b[19]` and `.toString()`), and
it is documented as a gap rather than dressed up as a Buffer — it has no
`slice`, no `write` and no encodings.

Other engine issues the module works around, each marked at its use site:
[#3](https://github.com/UrubuCode/zun/issues/3) `.length` typed `u64`,
[#13](https://github.com/UrubuCode/zun/issues/13) `!x` on an `any` empty string,
[#37](https://github.com/UrubuCode/zun/issues/37) (designed out: `ERR_INVALID_URI`
is a real `URIError` subclass with `code` as a declared field). Two further new
`__qsToString` carries two more notes, because `escape` is specified in terms of
exactly that conversion: ToPrimitive does not fall back from a non-callable
`toString` to `valueOf` (`String({ toString: 5, valueOf: () => 'x' })` answers
`'[object Object]'` instead of `'x'`, and `String({ toString: 5 })` answers
`'[object Object]'` instead of throwing — a new bug, reported with this work),
and Node converts a *non-object* with `str += ''`, which throws for a symbol,
while `String(aSymbol)` legitimately answers `'Symbol(x)'` — so the symbol
rejection is written out rather than delegated to `String`.
