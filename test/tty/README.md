# `node:tty` against Node.js 25's own tests

The bar for [`src/tty/tty.ts`](../../src/tty/tty.ts) is Node's own
`test/parallel/test-tty-*.js` and `test/parallel/test-ttywrap*.js` at
`v25.0.0` — 5 files. The pass count and the per-test table are regenerated by

```sh
bash tools/run_node_tests.sh --zun <path/to/zun> --module tty
```

and land in [`RESULTS.md`](RESULTS.md); the current figure is **2 / 5**. `tty`
is a `zun-ts` module and takes no `--ext`, which is a constraint rather than a
convenience: `node:tty` is required by the `console` corpus
(`test-console-tty-colors*.js`), which is `zun-ts`, so a `tty` that imported a
native would make those bundles fail to compile.

This module replaces the `__node_tty` stub that used to live in
`tools/harness/common.ts` (`isatty()` hard-coded to `false`,
`ReadStream`/`WriteStream` absent). `common.getTTYfd()` now searches fds 0–2
with the real predicate instead of answering `-1` unconditionally.

## Where the seam is

A TTY in Node is a libuv handle — `uv_tty_init(fd)`, then `setBlocking`,
`uv_tty_get_winsize` and `uv_tty_set_mode` on it. This runtime has none of
those; what it has is the three standard streams and an `isTty(fd)`
predicate. So:

| member | what this module answers |
|---|---|
| `isatty(fd)` | the real predicate, for any fd — `src/process/process.ts`' `__processIsTty`, which reads the `node:process` extension's `isTty(fd)` or the `zun:core` host's single `isTty()` flag |
| `new WriteStream(fd)` | a `Duplex` writing to fd 1 / 2 when that fd is a terminal; `ERR_TTY_INIT_FAILED` otherwise — which is what Node throws for a non-terminal fd as well |
| `new ReadStream(fd)` | the same shape over fd 0 |
| `ERR_INVALID_FD` | exact: `RangeError`, code `ERR_INVALID_FD`, message `"fd" must be a positive integer: -1` |
| `getColorDepth` / `hasColors` | `lib/internal/tty.js`' whole environment table, statement for statement |
| `cursorTo` / `moveCursor` / `clearLine` / `clearScreenDown` | `readline`'s own functions, reached **through `__node_readline`** rather than directly, because that indirection is observable (`test-tty-backwards-api.js` replaces them) |
| `columns` / `rows` / `getWindowSize()` | `undefined` / `[undefined, undefined]` — a gap, see below |
| `setRawMode(flag)` | records `isRaw`; the terminal mode is not changed — a gap, see below |

Under the test runner the three standard streams are pipes, so `isatty` is
`false` for all of them and `new tty.WriteStream(1)` throws
`ERR_TTY_INIT_FAILED` — which is exactly what `node` itself does when its
stdout is a pipe.

### `getColorDepth`, verified

The table is the bulk of the module, and it is Node's in Node's order:
`FORCE_COLOR` first (and its one-time warning when it overrides `NO_COLOR` /
`NODE_DISABLE_COLORS`), then `NODE_DISABLE_COLORS` / `NO_COLOR` /
`TERM=dumb`, then the Windows build-number branch, then `TMUX`, Azure DevOps
(`TF_BUILD` + `AGENT_NAME`), the eight CI vendors, TeamCity's version regexp,
`TERM_PROGRAM` (iTerm's version split, HyperTerm, MacTerm, Apple_Terminal),
`COLORTERM=truecolor|24bit`, the `TERM` regexps and the `dircolors` table, and
finally plain `COLORTERM`.

Measured here: `{}` → 4 (`COLORS_16`, the Windows branch), `FORCE_COLOR=1` →
4, `=2` → 8, `=3` → 24, `=x` → 1, `NO_COLOR=1` with
`TERM=xterm-256color` → 1, `TERM=dumb` → 1. `hasColors({FORCE_COLOR:'1'})` →
`true`, `hasColors(256, {FORCE_COLOR:'1'})` → `false`,
`hasColors(256, {FORCE_COLOR:'2'})` → `true`, `hasColors(1, {})` →
`ERR_OUT_OF_RANGE`.

The bundler has no `internal/test/binding`, so it never reaches the engine. ## New engine finding, with repro

### Deep recursion overflows the native stack instead of throwing `RangeError`

```js
async function test() { await test(); }
(async () => { try { await test(); } catch (err) { console.log(err); } })();
```

Node prints `RangeError: Maximum call stack size exceeded`. Zun aborts with
`thread '<unknown>' (NNNN) has overflowed its stack`, so the `catch` never
runs. The same happens for a plain synchronous
`function deep(n: number): number { return deep(n + 1); }`, so it is the
interpreter's frame budget rather than anything about promises. Checked
against the open *and* closed issue lists (`--state all`); no entry covers it. There is no sensible library workaround — a stack depth
limit belongs to the interpreter — so it is recorded here and the test is left
failing.

## Shapes that differ from Node, and why

* **window size.** Node reads it from the libuv handle. There is no native for
  it here, so `columns`/`rows` stay `undefined` and `getWindowSize()` answers
  `[undefined, undefined]` — the same shape Node reports when
  `uv_tty_get_winsize` fails, and the same thing `process.stdout.columns`
  already answers in this library. `_refreshSize()` is a no-op rather than an
  `'error'` emitter, because a size that cannot be read also cannot be seen to
  change.
* **the Windows branch of `getColorDepth`.** Node refines 16 colours to 256
  (build ≥ 10586) or 16m (build ≥ 14931) from `os.release()`. `node:os` is a
  native extension here and a `node:tty` bundle runs without one (see above),
  so the release is unknown and the answer is Node's own pre-Windows-10
  fallback, `COLORS_16`. `__ttyOSReleaseParts()` is the single function that
  would change if a release ever became readable without an extension.
* **raw mode.** `uv_tty_set_mode` has no counterpart in this runtime, so
  `setRawMode` records `isRaw` and leaves the terminal alone — the same no-op
  `process.stdin.setRawMode` already is. A consumer that depends on raw mode
  sees cooked input; nothing claims otherwise.
* **`ERR_TTY_INIT_FAILED`'s name.** Node's is a `SystemError`. The code, the
  message and the `info` object (`code`, `message`, `errno`, `syscall`) are
  reproduced; the name reads `Error`.
* **`net.Socket`.** Node's two streams are sockets. There is no `node:net`
  here, so they are `Duplex`es from `src/stream/stream.ts` — the part every
  consumer touches (`write`, `isTTY`, the `EventEmitter` surface) with no
  socket underneath.
