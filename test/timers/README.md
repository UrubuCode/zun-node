# Node.js v25 `timers` corpus

The bar for `node:timers` + `node:timers/promises` is Node's own
`test/parallel/test-timers*.js` — 58 files at `v25.0.0`, listed in
[`NODE_TESTS.txt`](NODE_TESTS.txt). The per-test result, with the first line of
each failing run's stderr, is in [`RESULTS.md`](RESULTS.md), regenerated by

```sh
bash zun-node/tools/run_node_tests.sh --zun target/debug/zun --module timers
```

`timers` is a **`zun-ts`** module: the VM owns the event loop (NUCLEUS §9a), so
there is no native extension and no `--ext`. Each test is bundled by
`tools/bundle_node_test.sh` and run as `zun run <bundle.ts>`.

## The one thing to know before reading the table

`setTimeout`, `setInterval`, `setImmediate`, `clearTimeout`, `clearInterval` and
`queueMicrotask` are *globals* in Node and **intrinsics** in Zun, with typed
parameters: the callback must be statically a function and a handle must be
numeric. Node's tests hand those functions an `any` (every `common.mustCall()`
result is one) and hand `clearTimeout` a `Timeout` object, `null`, a string or
`{}` — so without this module the intrinsic rejects most of the corpus at
compile time ([zun#29](https://github.com/UrubuCode/zun/issues/29)).

`src/timers/timers.ts` declares all six as top-level functions, which shadows
the intrinsics program-wide, and reaches the VM's macrotask tier through the
namespace import instead:

```ts
import { timers as __timerCore } from "zun:core";
__timerCore.setTimeoutArgs(callback, delay, args);
```

That is the spelling zun#29 asks for. It works for two reasons: a `zun:core`
namespace member call lowers straight to `call.builtin`, so the bare-name
shadow never sees it; and the native's callback parameter is `Opaque`, so an
`any`-typed callable is accepted there and nowhere else.

## Repros for the two new engine bugs

A bare `return` where the inferred return type is `Any`:

```ts
function take(fn: any): void { const f: any = fn; f("x"); }
take((v: any) => {
  if (v === "stop") return;          // error: [SEM0001] expected a Any return value
  return String(v).split(",");
});
```

`node` prints nothing and exits 0; `zun run` rejects the program at line 3.

An explicit `[Symbol.toPrimitive]()` call:

```ts
class Box {
  v: number = 0;
  [Symbol.toPrimitive](): number { return this.v; }
}
const b = new Box();
b.v = 7;
print(String(+b));                      // 7 — the implicit coercion is fine
print(String(b[Symbol.toPrimitive]()));  // panic: expected object, found Void
```

`crates/zun_interp/src/value.rs:228`. Both a typed and an `any`-typed receiver
panic; `+b`, `` `${b}` `` and `Number(b)` all work.

## Direct verification

Because half the corpus is blocked on things that are not `timers`, the module
was also checked **against Node directly**: one driver, 33 assertions, run
unchanged under `node` and under `zun run` — `failures=0` on both.

It covers `timers/promises` end to end (`setTimeout` with and without a value,
`setImmediate`, `scheduler.wait`, `scheduler.yield`, the `setInterval` async
iterator with `break`, and its `AbortSignal` ending), the four validation errors
each promisified function raises and the order it raises them in, an
already-aborted signal and a signal aborted while the timer is pending for both
`setTimeout` and `setImmediate`, that a promisified timer settles *after* the
synchronous code that follows the call, the `Timeout` shape
(`hasRef`/`ref`/`unref` chaining, `_idleTimeout`, `_repeat` for both kinds,
`refresh()` returning the timer, `+timeout` being a number, and
`_destroyed`/`_idleTimeout === -1` after a clear), `clearTimeout` by number id
and by string id, `clearTimeout`/`clearInterval`/`clearImmediate` tolerating
`null`, nothing and `{}`, `validateFunction` on the callback,
`node:timers`' exports being the same functions as the globals, argument
forwarding to a callback, and `queueMicrotask`'s own validation.

One divergence is **deliberately outside** that driver: an `unref()`'d
promisified timer. In Node, `await setTimeout(1, 'r', { ref: false })` with
nothing else holding the loop open never settles — the process just exits. Under
the harness it does settle, because the settle loop is itself keeping the VM
alive. That is a property of the harness, not of this module, and it is why the
`ref: false` case is asserted on `Timeout.hasRef()` rather than on a resolution.

The fix that came out of this pass is worth naming: `clearTimeout(id)` with a
**string** id panicked the interpreter. Node spells the first test
`timer?._onTimeout`, which is simply `undefined` for a string — here, reading an
undeclared property off a string held in an `any` aborts the run
(`expected object, found Str("16")`, `crates/zun_interp/src/value.rs`; a
*number* receiver answers `undefined` correctly). The receiver is narrowed with
`typeof` before the probe now, and that is a third new engine bug from this work:

```ts
function probe(v: any): any { return v._onTimeout; }
print(String(probe("16")));   // panic: expected object, found Str("16")
print(String(probe(16)));     // undefined — correct
```

## Deviations this module documents rather than hides

- **`this` inside a timer callback** is undefined, not the `Timeout`. A callable
  held in an `any` can only be reached as `fn(...args)`; `apply`/`call` thread no
  receiver ([zun#1](https://github.com/UrubuCode/zun/issues/1)).
  `test-timers-this.js` passes anyway, because its assertions run inside
  callbacks that never execute for an unrelated reason — it is listed as a pass
  with that caveat.
- **`setImmediate` versus `setTimeout(fn, 0)`** interleave in arm order rather
  than by loop phase (see the last table row).
- **`async_hooks`** does not exist, so no `destroy` hooks are emitted. The id a
  `Timeout` coerces to is a plain counter, which is all the observable contract
  of `[Symbol.toPrimitive]` needs.
- **`process.nextTick` and microtasks share one queue** (that is `process`'s own
  deviation, documented in `src/process/process.ts`), so a `nextTick` scheduled
  from inside a promise reaction runs after it rather than before.

## What the harness gained from this module

The settle loop in `tools/harness/common.ts` used to be a heuristic about
pending timers: it counted a turn idle whenever `process.nextTick` had nothing
queued, and work on the VM's own timer heap was invisible to it. Now that every
Node timer goes through `src/timers/timers.ts`, the loop asks it two questions —
`__timerPendingRefs()` (how many **ref'd** timers are armed) and
`__timerNextDelay()` (how long until the earliest is due) — and uses the first to
stay awake and the second as its own next delay, so the VM's virtual clock jumps
straight to the due time instead of spending one turn per millisecond. An
`unref()`'d timer is deliberately not counted, which is exactly what Node also
declines to wait for.

The loop also emits `process` 'beforeExit' now, re-running if a listener
schedules more ref'd work, and calls `__timerShutdown()` after 'exit' — the VM
re-arms whatever is in its timer heap, so an abandoned unref'd interval would
otherwise hang the run where Node would simply have returned from the loop.
