# Node.js v25 `diagnostics_channel` corpus

The bar for `node:diagnostics_channel` is Node's own
`test/parallel/test-diagnostics-channel*.js` — 49 files at `v25.0.0`, listed in
[`NODE_TESTS.txt`](NODE_TESTS.txt). The per-test result, with the first line of
each failing run's stderr, is in [`RESULTS.md`](RESULTS.md), regenerated by

```sh
bash zun-node/tools/run_node_tests.sh --zun target/debug/zun --module diagnostics_channel
```

`diagnostics_channel` is a **`zun-ts`** module: a channel is a map, a list and a
few calls, with no syscall anywhere, so there is no native extension and no
`--ext`. Each test is bundled by `tools/bundle_node_test.sh` — which inlines
`src/async_hooks/async_hooks.ts` ahead of it, because `bindStore`/`runStores`
are defined in terms of an `AsyncLocalStorage` — and run as
`zun run <bundle.ts>`.

## The shape of the corpus

Half of this corpus is not about `diagnostics_channel` at all. Node ships
*instrumentation* for its own subsystems on top of this module, and twenty-four
of the 49 files exercise that instrumentation rather than the channels: thirteen
`test-diagnostics-channel-http2-*`, two `-http*`, two `-net*`, one `-udp`, one
`-worker-threads`, four `-module-{import,require}{,-error}` and one `-process`
(which needs `cluster` *and* a `ChildProcess` with streams). They require
`node:http`, `node:http2`, `node:net`, `node:dgram`, `node:worker_threads`, the
CJS `require` hook or `node:cluster` — none of which exists in this library — so
twenty-two of them fail on the bundler's unresolved-`require` check; the two
`-module-import*` files bundle cleanly and then find that nothing instruments
the ESM loader, so their channels never publish. They are counted in the
denominator because Node counts them, but nothing in this module can move them.

The remaining twenty-five are the module itself — the named-channel surface, the
object-channel surface, `bindStore`/`runStores`, and the fifteen
`tracingChannel` files — and twelve of those pass.

### One pass that is counted and should not be trusted

`test-diagnostics-channel-tracing-channel-promise-run-stores` exits 0 and the
tracker scores it green, but it passes for the wrong reason and is recorded here
so nobody reads that green as working async context propagation. The test's
assertion is `store.getStore()` *after* an `await` inside `run()`:

```js
channel.tracePromise(common.mustCall(async () => {
  assert.deepStrictEqual(store.getStore(), firstContext);
  await setTimeout(1);
  assert.deepStrictEqual(store.getStore(), firstContext);   // undefined here
}));
```

The second assertion fails — `store.run()`'s `finally` has already restored the
previous value by the time the continuation resumes, because
`AsyncLocalStorage` here is a synchronous context (see
`src/async_hooks/async_hooks.ts`' header: the propagation is a VM facility —
V8 promise hooks plus libuv async-resource bookkeeping — and cannot be
synthesized from the language side). The `AssertionError` is thrown inside an
`async` function nobody awaits, so it becomes an unhandled rejection, and
nothing in this VM reports one. A minimal demonstration:

```js
store.run({ foo: 1 }, async () => {
  console.log('before await', store.getStore());   // { foo: 1 }
  await delay(1);
  console.log('after await', store.getStore());    // undefined  (node: { foo: 1 })
});
```

## Repros for the two new engine bugs found by this work

### 1. An omitted optional parameter arrives as `null` when the method also declares a rest parameter

```ts
function mk(context: any): any { if (context === undefined) return {}; return context; }
class K {
  m(fn: any, context?: any, thisArg?: any, ...args: any[]): any {
    const ctx: any = mk(context);
    ctx.result = 1;                 // aborts when `m` was called with one argument
    return ctx.result;
  }
}
const k: any = new K();
k.m(1, undefined);                  // fine
k.m(1);                             // zun: panic at crates/zun_interp/src/value.rs:228
```

`zun run` prints

```
thread '<unnamed>' panicked at crates\zun_interp\src\value.rs:228:22:
expected object, found Null
```

`node` prints nothing and exits 0 — in both calls `context` is `undefined`, so
`mk` answers a fresh object. Here the *omitted* argument reaches `mk` as `Null`
rather than `Void`, `context === undefined` is false, `mk` hands the `Null`
straight back, and the first member write on it aborts the process. Dropping the
rest parameter from `m` makes the panic go away, which is what points at the
dynamic-call argument padding (`dynamicCall0..6`,
`crates/zun_interp/src/collections.rs:2721`) rather than at the optional
parameter itself.

This is why `__dcContext` in `src/diagnostics_channel/diagnostics_channel.ts`
treats `null` as absent, and why `Console.prototype.timeLog` in
`src/console/console.ts` decides absence from `arguments.length` instead of from
the value — `console.count(null)` has to keep answering `null: 1`.

### 2. `x instanceof C` where `C` is an `any`-typed binding holding a class

```ts
class Ch {}
const mod: any = { Ch: Ch };
const inst: any = new Ch();
const C2: any = mod.Ch;             // typeof C2 === "function"
inst instanceof Ch;                 // true
inst instanceof C2;                 // zun: runtime error, uncatchable
```

`zun run` prints

```
zun: runtime error: call did not resolve to a method at <main> [349..351]
```

`node` prints `true`. The checker's `check_instanceof_operator`
(`crates/zun_sema/src/check.rs:15394`) sees a right operand whose type is `Any`
and lowers the whole thing to `typeinfo`'s `instanceofDynamic`, which dispatches
`C[Symbol.hasInstance](value)`. A *class* value has no such method — adding
`static [Symbol.hasInstance]` to the class does not help — so the dispatch fails
at run time and the failure is not catchable. [zun#72](https://github.com/UrubuCode/zun/issues/72)
is the compile-time half of the same gap (`x instanceof ns.Ctor` is rejected
outright).

Two of Node's own tests for this module are written as
`const dc = require('diagnostics_channel'); const { Channel } = dc;` followed by
`assert.ok(channel instanceof Channel)`, so the bundler keeps `Channel` bound to
the top-level class by dropping that one-name destructuring — the same move the
`events`/`EventEmitter` rule already makes, one indirection further along. See
the comment in `tools/bundle_node_test.sh`.

## Deviations this module documents rather than hides

- **`thisArg` is not a receiver.** `Channel.runStores`, `traceSync`,
  `tracePromise` and `traceCallback` all accept `thisArg` positionally and
  forward every argument after it exactly, but the traced function runs with
  `this === undefined` (zun#1). Seven of Node's tests measure precisely this, and an eighth (`-tracing-channel-callback`) would once zun#10 lets its seven-argument call compile.
- **`AsyncLocalStorage` is a synchronous context.** `run`, `exit`, `enterWith`,
  `disable` and `getStore` are exact for the synchronous extent of a callback,
  and nest correctly; a context does not survive an `await` or a scheduled
  callback. `src/async_hooks/async_hooks.ts` says why, and says it in its header
  rather than in a comment nobody reads.
- **One `Channel` class, no prototype swap.** Node moves a channel between
  `Channel` and `ActiveChannel` with `ObjectSetPrototypeOf`; there is no
  prototype model to move an object between here
  ([zun#25](https://github.com/UrubuCode/zun/issues/25)), so one class branches
  on `_subscribers === undefined`, which is the predicate the swap encodes. Every
  observable consequence is kept, including `hasSubscribers` answering `true` for
  a channel whose only registration is a bound store.
- **Weak channel references are pruned on access, not by a finalizer.** The
  `WeakRef` is real (held in a declared, typed field — read back out of an `any`
  slot the same object has no `deref`), and the refcount that makes it strong
  while something is subscribed is real. `FinalizationRegistry.register`,
  though, resolves only where the receiver's static type is known at the call
  site, and a module-level `const` stops being that as soon as the call moves
  inside a function — so a dead entry is dropped the next time the map is asked
  about that name instead. Nothing can observe an entry whose channel has
  already been collected, and Node's own comment says only GC is a valid time to
  clean the map up.
- **A subscriber that throws** is contained and re-raised through
  `process.nextTick`, as in Node. With a `process.on('uncaughtException')`
  listener installed it is emitted there (which is what
  `test-diagnostics-channel-safe-subscriber-errors.js` checks); with none, it is
  reported on stderr and `process.exitCode` becomes 1, which is Node's
  behaviour minus the immediate abort.

## What the rest of the library gained from this module

`src/async_hooks/async_hooks.ts` is the first `AsyncLocalStorage` in the tree,
and it took a test off another corpus's blocker list on arrival:
`test-timers-clearImmediate-als.js` required `async_hooks` and now passes
(`timers` went from 26 to 27). `src/console/console.ts`' five `console.<level>`
channels are the first consumer of this module inside the library —
`test-console-diagnostics-channels.js` passes because both halves exist.

`events`' three Node error bases also grew the `toString()` Node's own coded
errors carry (`` `${this.name} [${code}]: ${this.message}` ``), because
`assert.throws(fn, /ERR_SOMETHING/)` matches the regular expression against
`String(err)` and `test-diagnostics-channel-symbol-named.js` is written that way.
`err.name` is still the plain `"TypeError"`, exactly as in Node.
